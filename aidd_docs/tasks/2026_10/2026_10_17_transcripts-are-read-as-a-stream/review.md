### Findings

- `aidd_docs/product/usage-contract.md:343` : "an ingest holds 1 MiB and its longest line, whatever the transcript's size" overstates the bound. The use case still keeps every record and every unrecognised line that names a directory (`read-usage-use-case.ts:64`, `dropped`), which `contract.md` Limits states and this row leaves out. The longest line is also held about three times at its peak: the pieces, the joined buffer and the decoded string. The same claim appears in `cli/aidd_docs/memory/telemetry.md:33`. → say "a block, a few copies of its longest line, and what the reading keeps (records, unrecognised lines naming a directory)", or link the Limits — 🟢 minor, fit
- `cli/src/contexts/telemetry/infrastructure/claude-transcript-source-adapter.ts:58` : `Buffer.concat([...pieces, read.subarray(start, end)])` allocates and copies every line, even when `pieces` is empty, which is the common case with a 1 MiB block. This is correct, just one avoidable copy per line → `pieces.length === 0 ? read.toString("utf8", start, end) : Buffer.concat(...)` — 🟢 minor, performance
- `cli/src/contexts/telemetry/infrastructure/claude-transcript-source-adapter.ts:51` : a file rewritten in place (same inode) during the read can produce one spliced line and a wrong resume offset. The read used to be a single `pread`; it is now up to about 400 block reads, interleaved with the line reader's work, so the window grows from microseconds to seconds. Scenario: block k ends mid-line and keeps `"bb"` in `pieces`; the file is truncated and rewritten past `at`; block k+1 reads new bytes, and `"bb"` joined to the new bytes is handed over as one line (most likely unrecognised); `consumed` then lands inside the new content. Because identity is unchanged and size is at least the saved size, the next ingest resumes there and skips the new head. Claude transcripts are append-only, and the old reader had the same class of bug in a narrower window, so this does not block → after the loop, re-`fstat` the handle and do not advance past an offset the file has since dropped below, or document the case in the usage contract — 🟢 minor, error-handling
- `cli/tests/helpers/whole-transcript-reader.ts:51` : `identityOf` copies the adapter's private function (`claude-transcript-source-adapter.ts:21`). If the two ever drift, S1 fails loudly, so the oracle is safe, but the copy is still duplication. The `FileHandle.prototype.read` spy setup is also repeated in `claude-transcript-source-adapter.integration.test.ts:55` and `read-usage-use-case.integration.test.ts:188` → accept as a frozen oracle, or export `identityOf` — 🟢 minor, rot

### Findings

- `cli/src/contexts/telemetry/infrastructure/claude-transcript-source-adapter.ts:135-138` : the path-identity branch protects against no splice and loses data. The open handle stays bound to the inode it opened, so a file replaced at its path (rename over) is still read whole and consistently; only an in-place rewrite of the same inode can splice. Dropping that read means the old file's unread lines are never counted: probe in a sandboxed copy, `"aaa\nbbb\n"` replaced by `"zzz\n"` after the first line, read in blocks of 4 → first read handed `["aaa","bbb"]` and position `null`, next read from the kept position handed `["zzz"]` only; round 1's code counted `aaa`, `bbb` and saved the old identity, so the next read restarted on the new file anyway. This also contradicts the docs, which say the transcript "is read again from where it stood" (`aidd_docs/product/usage-contract.md:344`, `cli/aidd_docs/memory/telemetry.md:33`, `contract.md` "Changed under the read"): the replaced file is gone, never read again. With Claude Code's own set-aside (rename away to `*.jsonl.superseded-*`, a listed path read from 0 next time, then folded by key in `upsertUsage`) nothing is lost, only re-read, which is why this is not critical. Second scenario: a transcript replaced at its path during every read gets `null` every time, each next read restarts on the newer inode and is discarded again, so nothing at that path is ever counted; round 1 converged, saving the old identity and restarting cleanly → keep the size check on the handle, drop the `stat(path)` identity check (and its test at `claude-transcript-source-adapter.integration.test.ts:390`, rewritten to expect the old file's lines and its identity), and drop "or another file at its path" from the three docs — 🟡 major, correctness
- `cli/src/contexts/telemetry/infrastructure/claude-transcript-source-adapter.ts:39-40` : the docstring still says "Memory is a block and the longest line, whatever the range", which the round-1 fix corrected everywhere else (about three copies of the longest line) → align it, or point to `cli/aidd_docs/memory/telemetry.md` — 🟢 minor, coherence
- `cli/src/contexts/telemetry/infrastructure/claude-transcript-source-adapter.ts:53` : "Shorter than it was when stat'd: what is left is read next time." now describes a read that returns no position, so nothing of it is kept, not "what is left" → "Shorter than when stat'd: the read is discarded below" — 🟢 minor, coherence
- `cli/src/contexts/telemetry/infrastructure/claude-transcript-source-adapter.ts:135` : `stat(path)` rethrows anything but `ENOENT` (`absentIsNothing`, `:14-17`), so an `EACCES` or `ENOTDIR` on the path after a successful read now rejects the whole ingest where round 1 returned the read. Goes away with the first finding's fix; otherwise treat any stat failure as "not replaced" — 🟢 minor, error-handling
