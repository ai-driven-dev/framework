## Rules

| Rule   | Why it applies |
| ------ | -------------- |
| A guard ships with the mutation that proves it (`aidd_docs/memory/coding-assertions.md`) | each new rule and command has a test its mutation turns red |
| No code for an input never observed in real data (`aidd_docs/memory/coding-assertions.md`) | composite tokens in `tokens.css` and Vue or Svelte links stay written limits |
| A plugin never holds its own tests; run the scripts suite wrapped (`aidd_docs/memory/testing.md`) | tests in `scripts/__tests__/`, temp git repositories under the wrapper |
| A skill never links outside itself (`aidd_docs/memory/architecture.md`) | the skill names the engine by the plugin's `hooks/` path and stops when it is absent, never by a relative link |
| No dates or ticket IDs in code, tests or docs (`.claude/rules/01-standards/2-tracker-ids.md`) | fixtures and skill examples name date-free task folders |
| Gouvernail and Kairos are read only | pilots run on copies in the scratchpad, without `node_modules`, nothing installed |

## Decisions

| Decision   | Why |
| ---------- | --- |
| A render loads `../tokens.css` instead of carrying token values; the engine's `tokens` command regenerates that one file | a token change then reaches every render without rewriting one; markup that must change is rewritten by the skill from the impact report, which no deterministic command can do |
| `impact <id or token>…` prints the reached records, renders and code files as JSON | the change flow reads the impact from the engine, the same graph the hook uses, never from the model's memory |
| An edit is checked against the committed record only when that record is validated or deprecated, and status, `implemented-version`, `code` and History are not edits | a proposed element is still being designed; a review, a code catch-up or a history row raises no version |
| Kairos's design system covers its web apps; the Expo app is a written limit | the spec rules out two systems and non-web rendering |
